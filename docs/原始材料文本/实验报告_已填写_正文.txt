二、需求分析
2.1 业务问题与用户目标
填写提示：说明当前V1.0准备解决的业务问题，识别主要用户，并说明不同用户希望通过系统完成什么。不要直接罗列页面或按钮。

校园活动管理系统 V1.0 解决的是校园活动信息分散、学生获取活动信息和报名不便，以及活动组织教师发布活动和统计报名情况效率较低的问题。
系统主要面向两类用户。学生的核心目标是：通过统一入口查看校园活动的时间、地点和内容，完成报名与取消报名，并随时查看自己的报名情况。活动组织教师的核心目标是：自主发布和维护校园活动信息，并查看每个活动的报名学生情况。
因此，V1.0 的核心业务过程确定为“教师发布活动—学生查看活动—学生报名—教师查看报名信息”，并围绕该过程控制版本范围。

2.3 需求取舍与范围控制
填写提示：说明哪些候选需求没有进入V1.0，以及为什么暂不实现。重点体现小组如何控制版本范围，而不是追求功能数量。

第一，暂不实现消息通知功能（短信、邮件、系统推送）。该功能需要额外的通知机制，且不是“发布—报名”基本流程成立的必要条件，因此不纳入 V1.0。
第二，暂不实现活动审核与多级管理。V1.0 由活动组织教师直接发布和管理活动，以降低权限与业务流程复杂度，优先保证核心业务能够完整运行。
第三，暂不实现活动评价、积分与推荐等扩展功能。这些功能可以提升系统完整性，但不是当前版本要解决的核心业务问题，留待后续版本考虑。
通过上述取舍，V1.0 集中于身份管理、活动信息管理、学生报名与报名信息查看等核心能力。
三、工程意图
填写提示：工程意图应来源于已确认需求，并在编码前形成。内容应能够指导设计、实现和验证。

建设目的
建立一个支持校园活动基本组织与参与流程的信息化系统，解决活动信息分散、学生报名不便、教师统计报名情况效率低的问题。系统通过统一管理用户、活动与报名信息，使学生能够方便地了解并参与校园活动，使教师能够完成活动的发布、维护与报名信息查看。本版本不追求复杂功能与大规模系统，优先保证结构清晰、业务流程完整、能够实际运行。
本轮范围
本轮完成：用户注册与登录（按身份进入不同菜单）、活动列表与活动详情浏览、学生报名、取消报名、我的报名查看、教师发布活动、修改活动、关闭报名、删除活动、查看活动报名名单。
明确不在本轮范围：消息通知推送、活动审核与多级管理、活动评价与积分、活动推荐算法、第三方账号登录。
重要约束
①学生与教师具有不同的操作权限，登录后进入各自的菜单；②同一学生不能重复报名同一活动，由程序校验与数据库唯一约束双重保障；③只有处于可报名（OPEN）状态的活动才能报名；④教师只能修改、关闭、删除自己发布的活动，也只能查看自己活动的报名名单；⑤已有学生有效报名的活动不能直接删除；⑥密码不以明文保存，采用 SHA-256 加盐哈希后存入数据库。
完成依据
学生能够完成注册登录、浏览活动与活动详情、报名、查看我的报名与取消报名；教师能够完成活动发布、修改、关闭报名、删除与查看报名名单；核心业务过程“教师发布活动—学生查看活动—学生报名—教师查看报名信息”能够完整运行；针对上述功能编写的自动化测试用例全部通过（共 64 个）。

四、软件设计
4.1 总体设计
填写提示：用文字和必要图示说明系统采用的总体结构、主要组成部分及其关系。可插入系统结构图、模块图或其他能够指导实现的设计图。

系统采用控制台程序结构，由界面层（菜单交互）、业务逻辑层、数据访问层和数据库四部分组成。

界面层由 Java 控制台菜单实现，负责显示功能选项、接收键盘输入，把用户选择交给业务逻辑层处理，并输出执行结果。

业务逻辑层负责注册登录校验、活动信息维护、报名与取消报名等业务规则；数据访问层负责对数据库执行查询与更新操作。各层由普通 Java 类组成，通过方法调用协作，不引入任何框架。

数据库采用 MySQL，程序通过 JDBC 访问，主要保存用户、活动和活动报名记录等核心业务数据。

基本数据流：控制台菜单 → 业务逻辑层方法调用 → 数据访问层 → JDBC → MySQL。
4.2 核心业务流程
填写提示：至少选择一个V1.0核心业务过程进行说明，例如“学生查看活动并报名”或“教师发布并管理活动”。可以使用流程图、活动图或文字步骤。

本系统核心业务流程为“学生查看活动并报名”。

学生登录系统 → 程序验证账号密码及身份 → 查看活动列表 → 查看活动详情 → 判断活动是否处于可报名状态 → 提交报名 → 程序检查是否重复报名 → 未重复则创建报名记录 → 提示报名成功 → 学生可在“我的报名”中查看记录。

如果活动不可报名或学生已经报名，则程序拒绝本次报名操作并给出相应提示。

4.4 关键设计约束或决策
填写提示：记录对实现有实际影响的设计决策，例如身份与权限、重复报名规则、活动状态、数据校验、前后端组织方式等。

设计决策一：采用分层结构（界面层—业务逻辑层—数据访问层）。界面层只负责显示信息与读取输入，业务逻辑层负责业务规则校验，数据访问层通过 JDBC 执行 SQL。各层职责清晰：修改界面不影响业务规则，调整 SQL 也不影响界面。
设计决策二：区分学生与教师的权限。用户表用 role 字段区分身份，登录后进入不同菜单；同时业务层会再次校验“教师只能管理自己发布的活动”，避免仅依靠界面隐藏来实现权限控制。
设计决策三：使用独立的报名表并设置唯一约束。学生与活动是多对多关系，因此单独建立 activity_registration 表，并对 (activity_id, student_id) 建立唯一约束，从数据库层面保证同一学生不能重复报名同一活动。
设计决策四：取消报名采用状态变更而非删除记录。报名状态分为 REGISTERED 与 CANCELLED，取消报名只修改状态。这样既保留报名痕迹，也使学生重新报名时可以复用原记录，不会与唯一约束冲突。

6.3 重要调整记录（如有）
填写提示：仅记录对需求、工程意图、设计或实现产生明显影响的调整。普通代码修改和小问题修复无需在此重复记录。

调整一：总体实现方式由前后端分离改为纯 Java 控制台程序。原设计计划采用“Vue 3 前端 + Spring Boot 后端 + MyBatis-Plus”的结构；小组在实现阶段评估后认为该技术栈超出当前掌握范围，改为纯 Java 控制台程序 + JDBC 直接访问 MySQL。为此同步修改了报告 4.1 总体设计与 4.2 核心业务流程的表述，但需求（REQ-01～REQ-06）与数据设计（三张核心表）未发生变化。
调整二：活动时间字段类型由 DATE 改为 DATETIME。原设计只能保存日期，无法表达“上午 9 点开始”这类信息；改为 DATETIME 后可保存完整的开始与结束时间，并相应调整了建表脚本、实体类与数据访问层的时间转换。

BUG-01
教师删除一个已无有效报名的活动时，程序抛出数据库外键约束异常，活动无法删除。
该活动此前有学生报名后又取消，报名记录行仍保留在 activity_registration 表中（状态为 CANCELLED）。业务层只统计状态为 REGISTERED 的有效报名人数，判断为“可以删除”，但外键约束 fk_reg_activity 会因为子表仍有引用而拒绝删除活动。
在 ActivityService.delete() 中增加一步：先调用新增的 RegistrationDAO.deleteByActivityId() 清理该活动的全部报名记录（包括已取消的），再执行活动删除。
教师删除活动功能（REQ-05）；数据访问层新增方法 deleteByActivityId()。
重新运行 ActivityServiceTest，“有人报名时删除被拒绝”“无人报名时删除成功”“删除后查不到该活动”三个用例全部通过；数据库中不再残留已删除活动的报名记录。
BUG-02
数据库初始化脚本中演示账号的密码以明文 123456 保存，与工程意图中“密码不以明文保存”的约束不符。
编写建库脚本时先用明文占位，实现登录功能后未同步调整密码的存储方式。
新增 PasswordUtil 工具类（使用 JDK 自带的 MessageDigest 实现 SHA-256 加盐哈希），把 db/schema.sql 中的初始密码改为 64 位密文，并在 AuthService.login() 中改为“把用户输入重新哈希后与库中密文比对”。
db/schema.sql、util/PasswordUtil、service/AuthService；数据库 user 表的 password 字段。
