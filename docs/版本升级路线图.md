# 校园活动管理系统 —— 版本升级路线图

> 适用项目：校园活动管理系统（V1.0、V1.5 已完成）
> 本文档记录 V1.5、V2.0、V3.0 的升级目标、技术方案与验收标准，
> 同时也是 V1.0 报告中「暂不实现的功能留待后续版本考虑」的具体落地计划。

---

## 一、总览：各版本之间的关系

| 版本 | 主题 | 变更类型 | 技术栈变化 | 复用前一版本的部分 |
| --- | --- | --- | --- | --- |
| **V1.0**（已完成） | 跑通核心业务 | 功能实现 | 纯 Java 控制台 + JDBC + MySQL | —— |
| **V1.5**（已完成） | 前后端分离 | **技术架构升级**（需求不变） | 新增 JDK 内置 HttpServer 提供 REST 接口；新增 Vue 3 前端 | 需求、业务逻辑层、实体类、数据访问层、数据库结构**全部复用** |
| **V2.0**（进行中） | 需求演化 | **功能迭代**（需求变化） | 技术栈不变，沿用 V1.5 | 全部代码复用，按访谈结论增量修改 |
| **V3.0** | 换成主流后端框架 | 技术架构升级 | Spring Boot 3 替换手写 HTTP 层 + JDBC DAO | 前端**零改动**；业务规则与数据库设计基本不变 |

### 为什么 V1.5 不叫 V2.0？

V1.5 只换了「界面形态与通信方式」，**需求一条都没有变** —— 六项需求（REQ-01 ~ REQ-06）、
全部业务规则、数据库三张表的结构，都还是 V1.0 的。它属于**技术架构升级**，
不是需求驱动的迭代，因此不占用大版本号。

V2.0 留给「通过**需求访谈**获得新需求」的那一版（即实验二）。
这样版本号与需求文档严格对应，评审时一眼就能对上：

| 版本 | 对应的需求来源 | 对应交付物 |
| --- | --- | --- |
| V1.0 | 实验一的需求（REQ-01 ~ REQ-06） | 实验一报告 + 控制台程序 |
| V1.5 | 同 V1.0，**需求未变** | 不单独出报告，作为 V2.0 的技术基础 |
| V2.0 | 实验二的需求访谈结论 | 实验二报告 + Web 应用 |

**这张表本身就是 V1.0「设计决策一：采用分层结构」的价值证明**：
界面换了两次（控制台 → Vue 3 → 未来 Spring Boot），业务规则和数据访问不需要重写。
这一段可以直接写进 V2.0 报告的「影响分析」。

```
V1.0   MainMenu(控制台)   →          Service  →  DAO        →  JDBC  →  MySQL
V1.5   Vue3(浏览器) → HTTP → HttpServer(手写) → Service  →  DAO   →  JDBC  →  MySQL
V2.0   Vue3(浏览器) → HTTP → HttpServer(手写) → Service  →  DAO   →  JDBC  →  MySQL
                                  ↑ 与 V1.5 同架构，变的是需求
V3.0   Vue3(浏览器) → HTTP → Spring Boot      → Service  →  MyBatis-Plus → MySQL
                                    ↑ 只有这一层在变（V1.0 → V1.5 → V3.0）
```

## 二、V1.5：加入 Vue 3 前端（技术架构升级，已完成）

### 2.1 目标

把控制台菜单替换为浏览器界面，实现前后端分离，**但暂时不引入 Spring Boot**。

为实现这一目标，需要先用 Java 写一个轻量 HTTP 接口层。选择 JDK 自带的
`com.sun.net.httpserver.HttpServer`（无需任何框架和额外 jar），
目的是把「HTTP 接口」这件事本身先理解清楚，
而不是一上来就依赖框架的注解和自动配置。

**注意：本版本不新增、不修改任何业务需求**，只是给 V1.0 已有的六项需求换一个界面。

### 2.2 后端改造（新增一个界面层实现）

| 序号 | 任务 | 说明 |
| --- | --- | --- |
| B1 | 新增 `web` 包 | `com.hbk.activity.web`，与现有 `ui` 包平级，二者都调用同一套 Service |
| B2 | 实现 HTTP 服务器 | 用 `HttpServer.create(new InetSocketAddress(8080), 0)` 启动，线程池 `Executors.newFixedThreadPool` |
| B3 | 编写路由与处理器 | 每个功能一个 Handler，例如 `/api/auth/login`、`/api/activities`、`/api/activities/{id}/registrations` |
| B4 | 引入 JSON 处理 | 推荐把 `gson-x.x.jar` 放入 `lib/`（单 jar 无依赖），或手写一个简易 JSON 工具类练手 |
| B5 | 统一响应格式 | 统一返回 `{code, message, data}`，成功 code=0，失败带原因，前端只需判断 code |
| B6 | 登录令牌 | 登录成功后生成 UUID token，用 `Map<String, User>` 在内存中保存会话；请求头带 `Authorization: Bearer <token>` |
| B7 | 跨域处理 | 处理 `OPTIONS` 预检请求并返回 CORS 响应头（或由 Vite 代理规避） |
| B8 | 参数解析与校验 | 解析路径参数、查询参数与请求体；在接口层做非空校验，业务规则仍留在 Service |
| B9 | 启动入口调整 | 保留 `MainMenu` 作为控制台入口，新增 `WebServerMain` 作为接口服务入口，两个入口共用 Service |

### 2.4 V1.5 验收标准（已全部通过）

1. 浏览器打开前端页面能完成：注册 → 登录 → 浏览活动 → 报名 → 取消报名 → 我的报名；
2. 教师登录后能发布、修改、关闭、删除活动并查看报名名单；
3. 六项业务规则在**接口层被绕过前端直接调用时依然生效**（用 Postman / curl 直接调接口验证）；
4. 学生用教师接口、教师用学生接口会被拒绝；
5. 前端刷新页面后登录状态不丢失；
6. `MainMenu` 控制台入口仍可运行（证明 Service 层可被两种界面复用）。

### 2.5 与实验报告的关系

V1.5 **不是报告交付物**，实验一报告描述的仍然是 V1.0 的控制台形态，不必回头修改。

| 用途 | 说明 |
| --- | --- |
| 作为 V2.0 的基线 | V2.0 的「现状」就是 V1.5 的界面与接口，访谈中的问题都基于它提出 |
| 截图来源 | V2.0 报告中的「迭代前界面」可以直接用 V1.5 的页面截图 |

## 三、V2.0：基于需求访谈的需求演化（进行中 · 实验二）

### 3.1 目标

通过**对真实角色做需求访谈**，发现 V1.5 现有功能的不足，
把访谈结论整理成新需求，再据此迭代出 V2.0。

**硬性前提**：需求必须来自访谈，不能凭想象编造。

### 3.2 输入：需求访谈

| 步骤 | 产出物 |
| --- | --- |
| 1. 确定访谈对象 | 覆盖三类角色：**学生、教师、系统管理员** |
| 2. 设计访谈提纲 | 每个角色一组开放式问题（现状 → 痛点 → 期望） |
| 3. 实施访谈并记录 | 逐条记录问答原文（报告要求附访谈记录） |
| 4. 提取候选需求 | 从原话中提炼「用户故事 + 验收标准」 |
| 5. 冲突消解 | 找出角色之间互相矛盾的需求，说明取舍理由 |
| 6. 形成需求基线 | 确定本轮真正要做哪些需求（可分批） |

### 3.3 实现原则

- **技术栈不动**：仍然是 V1.5 的 Vue 3 + 手写 HttpServer + JDBC + MySQL；
- **能复用就复用**：新增需求优先在 Service 层扩展，界面层只做展示；
- **数据库增量修改**：新字段用 `ALTER TABLE` 追加，不推翻 V1.0 的表结构；
- **新增角色要成体系**：若访谈确认需要「系统管理员」，则在 `user.role` 中新增角色值，
  并在前端增加对应的路由、菜单与守卫，而不是临时打补丁。

### 3.4 V2.0 验收标准

1. 每一条新需求都能追溯到某一次访谈记录中的原话；
2. 用户故事有明确的验收标准，且逐条通过；
3. V1.5 已有的六项需求**全部不回归**（64 个用例 + 接口验证全部通过）；
4. 新增角色（若有）的权限边界清晰：越权访问同样被接口层拒绝；
5. 报告中给出「影响分析」：列出被修改的文件与未被修改的文件，说明原因。

### 3.5 对报告的影响

| 报告部分 | 需要写的内容 |
| --- | --- |
| 访谈记录 | 三个角色的问答原文 |
| 用户故事与验收标准 | 每条候选需求的卡片化描述 |
| 影响分析 | 新需求对现有架构、数据库、界面的影响 |
| 实现与测试 | 新功能的实现说明与验证结果 |

## 四、V3.0：换成 Spring Boot 3

### 4.1 目标

用 Spring Boot 替换 V1.5 手写的 HTTP 层与 JDBC 数据访问层，
体验主流框架解决的重复劳动问题，**前端一行代码都不用改**。

### 4.2 后端改造

| 序号 | 任务 | 对应 V1.5 的手写实现 |
| --- | --- | --- |
| S1 | 引入 Maven 工程 | `backend/pom.xml`：spring-boot-starter-web、mybatis-plus、mysql-connector-j、jjwt、spring-security-crypto、lombok（注意 JDK 版本兼容） |
| S2 | 启动类与配置 | `@SpringBootApplication`；`application.yml` 配置端口、数据源、JWT |
| S3 | Controller 层 | `@RestController` + `@GetMapping/@PostMapping` 替代手写路由与 Handler |
| S4 | 参数与响应 | `@RequestBody/@PathVariable/@RequestParam` 自动绑定；Jackson 自动序列化，替代手写 JSON |
| S5 | 参数校验 | `@Valid` + `@NotBlank/@Size` 替代接口层的手写 if 判断 |
| S6 | 统一响应与异常 | `Result<T>` 统一返回；`@RestControllerAdvice` 全局异常处理，替代每个 Handler 里的 try-catch |
| S7 | 数据访问层 | MyBatis-Plus 的 `BaseMapper` 替代手写 JDBC 增删改查；保留现有 SQL 语义 |
| S8 | 依赖注入 | `@Service/@Mapper` + 构造器注入替代 `new XxxService()` |
| S9 | 登录认证 | JWT（jjwt）替代内存 Map 会话；`HandlerInterceptor` 统一校验 token，替代每个 Handler 手动解析请求头 |
| S10 | 权限控制 | 自定义 `@RequireRole` 注解 + 拦截器，替代接口层手写角色判断 |
| S11 | 密码加密升级 | BCrypt（`BCryptPasswordEncoder`）替代 SHA-256 固定盐，自动随机盐、可调强度 |
| S12 | 事务管理 | `@Transactional` 保证"删除活动时先清报名记录再删活动"两步的原子性（**V1.0/V1.5/V2.0 都缺这一环**） |
| S13 | 连接池 | HikariCP（Spring Boot 默认）替代每次 `DriverManager.getConnection()` |
| S14 | 接口文档 | 集成 springdoc-openapi / Knife4j，自动生成接口文档 |
| S15 | 打包部署 | `mvn package` 打成可执行 jar，`java -jar` 启动 |

**包结构映射**（现有代码几乎可直接迁移）

| V1.0/V1.5 包 | V3.0 包 | 变化 |
| --- | --- | --- |
| `entity` | `entity` | 加 MyBatis-Plus 注解（`@TableName`、`@TableId`） |
| `dao` | `mapper` | 继承 `BaseMapper<T>`，删掉重复的 JDBC 样板代码 |
| `service` | `service` + `service.impl` | 加 `@Service`，改为接口 + 实现类 |
| `ui` / `web` | `controller` | 加 `@RestController`，方法体几乎不变（仍调用 Service） |
| `util.DBUtil` | 配置文件 + 连接池 | 被框架接管，可删除 |
| `util.PasswordUtil` | `BCryptPasswordEncoder` | 替换为框架提供的实现 |

4. 数据库结构与 V1.5/V2.0 兼容（D1~D8 属于可选增量，逐个加、逐个测）；
5. 打成 jar 后可在命令行独立启动。

## 五、遗留的技术债

按优先级排列。**状态一栏是本文件与代码实际核对后的结果**。

| 编号 | 问题 | 影响 | 状态 / 计划 |
| --- | --- | --- | --- |
| T2 | 数据库账号密码硬编码在 `DBUtil.java` | 换环境要改代码；有泄露风险 | ✅ **已在 V1.5 解决**（改为读 `config/db.properties`） |
| T1 | 删除活动时"先清子表再删主表"没有事务保护 | 中途失败会留下不一致数据 | V3.0（`@Transactional`） |
| T3 | 密码使用固定盐的 SHA-256 | 强度低于专用密码算法 | V3.0（BCrypt） |
| T4 | 每次操作都新建数据库连接 | 并发性能差 | V3.0（连接池） |
| T9 | 登录会话存在内存 Map（V1.5 方案） | 重启即失效、无法多实例 | V3.0（JWT） |
| T5 | "我的报名"列表逐条查询活动信息（`RegistrationService.myRegistrations`） | N+1 查询 | V2.0 或 V3.0（改为一次联表查询） |
| T6 | `UserDaoTest` / `ActivityDaoTest` / `RegistrationDaoTest` 只打印结果，没有断言 | 出问题不会自动报错 | V2.0（统一改成断言式测试） |
| T7 | `UserDaoTest` 会留下 `test_user_01` 测试数据未清理 | 污染数据库 | V2.0（补清理逻辑） |
| T10 | 缺少日志规范，接口层仍在用 `printStackTrace` 与 `System.out` | 排查问题困难 | V2.0（引入 `java.util.logging` 或 log4j2） |
| T8 | 接口无分页，数据量大时一次性返回 | 性能与体验问题 | V3.0（D4） |
