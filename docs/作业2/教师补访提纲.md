## 提问清单（9 问，按重要性排序）

| 序号 | 我的问题 / 追问 | 想问清楚什么 | 会影响哪个设计决策 |
| --- | --- | --- | --- |
| Q1 | 你发布一个活动之后，是马上就能被学生看到，还是要等平台（管理员）审核通过？ | **G5**——活动发布是否需要审核环节 | ⚠️ **影响面最大**：决定要不要做一整套「活动待审核 → 通过 / 驳回」流程，以及管理员端是否要加审核页面 |
| Q2 | 如果需要审核，你希望由谁来审、审哪些内容？万一没通过，你希望怎么知道原因？ | G5 的补充细节 | 决定审核的字段、通知方式与驳回理由 |
| Q3 | 有学生取消报名、空出一个名额之后，你希望系统**自动**把这个名额给候补的第一个人，还是你自己手动挑？ | **G7**——递补的触发方式 | 决定递补是写在服务端自动执行，还是做成教师端的一个操作按钮 |
| Q4 | 如果是自动给，要不要先通知候补的人确认一下？他要是没回应，名额怎么办？ | G7 的补充 | 决定要不要引入「待确认」状态与超时机制（会显著增加状态数） |
| Q5 | 如果一个活动**谁都能参加、没有额外条件**，学生报名后还需要你一条条点"通过"吗？ | **G8**——无条件活动的审核 | 决定报名后的初始状态：是统一进「待审核」，还是无条件活动可以跳过审核直接排位 |
| Q6 | 你刚才说「有些活动并不适合所有学生」。能不能举个例子，具体是哪种不适合？是限定年级、专业，还是要先通过选拔？ | **G3**——「参加条件」到底指什么 | 决定 `eligibility` 是**自由文本**还是**结构化字段**（若是结构化，设计复杂度差别很大） |
| Q7 | 这些条件你希望怎么告诉学生？写成一句话说明，还是从几个固定选项里选？ | G3 的呈现方式 | 决定教师端表单与学生端详情页的展示形式 |
| Q8 | 活动开始之前学生还能取消报名吗？要不要设一个时间点，过了这个点就不能取消了？ | **G6**——取消截止时间 | 决定要不要加截止时间字段与相应校验（V1.5 目前随时可取消） |
| Q9 | 审核学生报名的时候，你需要看到他的哪些信息？姓名、学号、年级、专业？ | ⭐ **本轮新提出** | ⚠️ **可能牵出新的数据字段**：目前 `user` 表只有 `username / password / name / role`。如果审核要看年级或专业，就得给 `user` 加字段，并让学生能维护这些信息 |

> **Q9 值得特别留意**：它是由 G3 推出来的连带问题。
> 如果 Q6 的答案是"限定年级/专业"，那 Q9 就必然要求 `user` 表新增字段——
> 这是一条**藏在需求背后的数据模型变化**，不追问很容易漏掉，
> 而漏掉它会在开发阶段才发现，代价更大。
