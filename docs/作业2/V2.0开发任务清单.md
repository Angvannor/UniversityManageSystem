## 二、阶段 1：数据库改造（P0）

### T1-1 修改 `db/schema.sql` ✅ 已完成

**实现方式说明**：`schema.sql` 本身是**重建脚本**（开头有 `DROP TABLE IF EXISTS`，
一直按「每次重置为演示数据」的方式使用），所以正确做法是**直接改 `CREATE TABLE` 定义**，
重跑脚本即得到 V2.0 表结构。对应的**增量 `ALTER` 语句**以注释形式保留在文件末尾
「附：增量升级语句」一节，用于在已有数据的库上升级，同时作为报告第八节
「数据/领域对象调整」的对照材料。

三张表都只做**加字段**，不改主键、不改唯一约束、不改外键。
`uk_reg_student_activity (activity_id, student_id)` **保持不变**（见 6.1 说明）。

| 表 | 新增内容 |
| --- | --- |
| `user` | `status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE'`（`ACTIVE` / `DISABLED`）；`role` 注释扩展为 `STUDENT` / `TEACHER` / `ADMIN`（`VARCHAR` 无 CHECK 约束，无需改结构） |
| `activity` | `capacity INT NULL`（NULL = 不限制）、`eligibility VARCHAR(500) NULL`（NULL = 无特殊条件） |
| `activity_registration` | `review_time DATETIME NULL`（审核时间，同时是候补排序依据）；`status` 默认值改为 `PENDING_REVIEW`，注释写入 5 个取值；新增索引 `idx_reg_activity_status (activity_id, status)` |

**历史数据迁移语义**（写在文件末尾的注释里）：V1.5 无审核环节，
原有 `REGISTERED` 视为已确定参加，迁移为 `CONFIRMED`。

## 三、阶段 2：实体与 DAO ✅ 已完成

### T2-1 ~ T2-3 实体类加字段 ✅

| 类 | 新增内容 |
| --- | --- |
| `entity/User.java` | `status` 字段；常量 `STATUS_ACTIVE` / `STATUS_DISABLED`；方法 `isDisabled()` |
| `entity/Activity.java` | `capacity`（**`Integer` 而非 `int`**，因为要能表示 NULL）、`eligibility`；方法 `hasCapacityLimit()` |
| `entity/ActivityRegistration.java` | `reviewTime` 字段；5 个状态常量 `STATUS_PENDING_REVIEW` / `STATUS_CONFIRMED` / `STATUS_WAITLISTED` / `STATUS_REJECTED` / `STATUS_CANCELLED`；方法 `isPendingReview()` / `isConfirmed()` / `isWaitlisted()` / `isRejected()` / `isCancelled()` / **`occupiesSlot()`** |

**三个关键设计决定**：

1. **`capacity` 用 `Integer` 而不是 `int`**：数据库该列允许 NULL 表示"不限制人数"。
   用基本类型 int 会把 NULL 读成 0，语义变成"一个人都不能报"。
2. **状态抽成常量**：状态字符串要在 DAO、Service、菜单、接口层反复使用，
   到处手写很容易拼错（如 `WAITLISTED` 写成 `WAITLISTEDD`），
   而编译器不报错，只在运行时表现为"判断永远不成立"，极难排查。
3. **新增 `occupiesSlot()`**：判断这条记录是否"占着报名资格"（待审核 + 候补 + 正式参加）。
   它是"不能重复报名"与"可以重新报名"的统一判据 ——
   处于 `CANCELLED`（学生自己取消）或 `REJECTED`（教师驳回）时不占资格，可重新报名并复用原行。
   原来的 `isRegistered()` 从未被任何代码调用过（死代码），已被它取代。

> **关于 `REJECTED` 能否重新报名**：访谈未覆盖，本轮按最小假设处理 ——
> 与 `CANCELLED` 一样允许重新报名（复用原行回到待审核）。
> 这样代码最简：只要不在「占位三态」里就能重报，与 V1.5 的判断形状完全一致。

### T2-4 ~ T2-6 DAO ✅

| 类 | 改动 |
| --- | --- |
| `UserDAO` | `COLUMNS` 加 `status`；`mapRow` 读取；`insert` 写入（**status 为 null 时兜底为 ACTIVE**，否则会往 NOT NULL 列绑 null 而抛异常）；**新增** `findAll()`（管理员看全部账号）、`updateStatus(id, status)`（停用/恢复） |
| `ActivityDAO` | `COLUMNS` 加 `capacity` / `eligibility`；`insert` / `update` 写入（**用 `setObject(?, 值, Types.INTEGER)` 显式给类型**，否则绑 null 时驱动不知该按什么类型发送）；`mapRow` 读取（**用 `getInt` + `wasNull()` 判断 NULL**，这是本阶段最容易踩的坑） |
| `RegistrationDAO` | `COLUMNS` 加 `review_time`；新增常量 `OCCUPYING_STATUSES`；**新增** `findByActivityIdAndStatus()`（名单分组）、`countByStatus()`（三类人数统计）、`findWaitlistOrderByReviewTime()`（**候补按进入候补时间排序**）、`updateStatusAndReviewTime()`（**状态与审核时间一条 SQL 一起写**）；`mapRow` 读取 `review_time`（**先判空再 `toLocalDateTime()`**）；`countRegistered()` 语义改为统计「占位三态」 |

**`countRegistered()` 与 `countByStatus()` 的分工**（容易混淆，特别说明）：

| 方法 | 统计口径 | 用在哪 |
| --- | --- | --- |
| `countRegistered(id)` | 待审核 + 候补 + 正式参加 | 界面显示"已报名 N 人"；判断活动能否删除 |
| `countByStatus(id, CONFIRMED)` | 只有正式参加 | **判断名额是否已满**（US-07 审核时的分支） |
| `countByStatus(id, WAITLISTED)` | 只有候补 | 名单页显示候补人数 |
| `countByStatus(id, PENDING_REVIEW)` | 只有待审核 | 名单页显示待审核人数 |

> 候补的人和待审核的人都**没有占住正式名额**，所以判断"满没满"必须用后三者，
> 不能用 `countRegistered()` —— 这是本轮最容易写错的一处业务口径。

### T2-7 阶段 2 冒烟测试（新增）✅

新增 `src/com/hbk/activity/tool/DaoV2SmokeTest.java`：**53 项断言全部通过**。

| 验证项 | 为什么必须验 |
| --- | --- |

| `countRegistered()` 只算占位三态 | 活动3 只有一条 `REJECTED`，应算 0 |
| `updateStatusAndReviewTime()` 能一次写入两列 | 状态与时间必须同一条 SQL 写，避免出现"候补但时间为空" |

## 四、阶段 3：业务层 ✅ 已完成

### T3-0 注册角色白名单（计划外新增，安全问题）✅

**做之前发现的一个权限提升漏洞**：`user.role` 是前端传上来的，
V1.5 只有学生和教师两种角色所以无所谓；V2.0 新增 `ADMIN` 之后，
任何人都可以构造一个注册请求把角色写成 `ADMIN`，**自己把自己变成系统管理员**。

修法：在 `AuthService.register()` 里加角色白名单，只允许 `STUDENT` / `TEACHER`，
`ADMIN` 只能由 `db/schema.sql` 预置（这也与最小假设 A2「不提供管理员建号功能」一致）。
同时给 `User` 补上 `ROLE_STUDENT` / `ROLE_TEACHER` / `ROLE_ADMIN` 常量。

### T3-1 `AuthService`：停用账号不能登录 ✅

**设计决定（改动最小的做法）**：`login()` 的签名**不变**，仍返回 `User`。
两条失败路径可以清楚区分：

| 情况 | `login()` 返回 | 调用方处理 |
| --- | --- | --- |
| 账号不存在 / 密码错误 | `null` | 错误码 **2001** |
| 密码正确但账号已停用 | `User`（`status = DISABLED`） | 错误码 **2003** |

由调用方（`AuthApi` 与控制台 `MainMenu`）在拿到 `user` 后检查 `status`。
这样不需要改 Service 签名，控制台入口也能复用同一判断。

> ⚠️ **这个设计的代价**：安全性依赖"每个调用方都记得检查"。
> 目前只有两个调用点（`AuthApi` 阶段 4 补、`MainMenu` 本阶段已补），可控；
> `login()` 的 javadoc 里写了醒目的警告。若将来调用点变多，
> 应当改成返回一个带状态码的结果对象，把检查变成强制的。

### T3-2 `ActivityService`：人数上限与参加条件的校验 ✅

新增私有方法 `checkAndNormalizeCapacity()`，`publish()` 与 `update()` 共用：

| 规则 | 说明 |
| --- | --- |
| `capacity` 为 `null` | **合法**，表示不限制人数（判断时必须先判 null，否则自动拆箱抛空指针） |
| `capacity <= 0` | 拒绝，提示"人数上限必须是大于 0 的整数，留空表示不限制人数" |
| `eligibility` 只输空格 | **规范化成 `null`**，避免库里存一堆空格、界面上"有条件"却显示空白 |
| `eligibility` 超 500 字 | 拒绝（与 `VARCHAR(500)` 一致，业务层先拦一道） |

### ⚠️ T3-7 发现并修复一个**会破坏演示数据的严重缺陷** ✅

阶段 3 跑测试时发现两个新测试在**批量连跑**时失败，追查后确认是**旧测试的 bug**，
而且它会**损坏数据库里的演示数据**：

| 出问题的测试 | 错误写法 | 实际后果 |
| --- | --- | --- |
| `ActivityDaoTest` | `afterInsert.get(afterInsert.size() - 1)` 取"列表最后一条"当作刚插入的活动 | `findAll()` 是**按 `start_time` 排序**的，"最后一条"是开始时间最晚的**书法体验课** —— 于是它被改名、关闭、**删除** |
| `RegistrationDaoTest` | `activities.get(activities.size() - 1)` 同上 | `findByTeacherId()` 同样按时间排序，"最后一条"是**校园歌手大赛** —— 学生的报名记录被写到了演示活动上，清理时**删掉了李同学在该活动的正式参加记录**，随后删活动被外键拦住 |

**根因**：把"列表最后一条"当成"我刚插入的那一条"。列表是**按业务字段排序**的，
不是按插入顺序，两者没有任何关系。

**修法**：直接用 `insert()` **回填的自增主键**（阶段 2 已经实现 `RETURN_GENERATED_KEYS`，
这两处过时的 workaround 本来就该删掉）：

```java
Long newId = activity.getId();   // 而不是取列表最后一条
```

**同时加固了新测试**：不再依赖精确的演示数据（用户数用 `>=`、
按标题而不是 id 找活动、报名相关的断言全部改为**自建临时数据**），
这样测试才能独立、可反复运行。

**验证**：重跑 `schema.sql` 恢复演示数据后，**连续跑两轮全部 8 个测试类**，
两轮均 0 失败，且演示数据完好（4 个活动含 `书法体验课`、6 条报名记录一条不少）。

> 这条发现可以直接写进报告第十节「测试中发现的问题及修正情况」——
> 它正是"测试之间必须相互独立"这个原则的具体案例。

### ⚠️ T4-10 一个排查出来的环境问题（记录备查）

测试输出里的中文全变成乱码，一开始以为是代码问题，
实际原因是 **Java 的 `System.out` 在输出被重定向时使用系统本地编码（GBK）**，
而 PowerShell 按 UTF-8 解码，两边对不上。

解决办法（只在跑测试时用，不影响项目本身）：

```powershell
$env:JAVA_TOOL_OPTIONS = "-Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8"
```

**这不影响功能**，只是让中文日志可读。写进报告时不必提，但排查过程值得记一笔：
"控制台乱码"很容易被误判成代码 bug，实际是编码问题。

### 7.4 新增了"一次跑完"的入口 ✅

给 `build.bat` 加了 `test-all` 目标，依次运行 9 个测试类（`ApiV2SmokeTest` 需要接口服务在跑，单独执行）：

```powershell
.\build.bat test-all
```

**踩到的坑**：`build.bat` 的换行符变成了 LF，而批处理文件必须是 CRLF ——
`cmd` 解析多行的 `for` 块时彻底错乱，输出几万行 `'e' is not recognized`。
已把文件恢复为 **ASCII + CRLF**，并在 `java` 命令里补上
`-Dstdout.encoding=UTF-8` 解决中文乱码。

### 7.5 回归测试结论（US-15）

V1.0 的六项业务规则在 `RegressionV2Test` §1 中**逐条验证，全部通过**，
并且在 V2.0 的新状态模型下依然成立：

| 规则 | 结论 |
| --- | --- |
| ① 同一学生不能重复报名同一活动 | ✅ |
| ② 只有 `OPEN` 的活动才能报名 | ✅ |
| ③ 取消报名只改状态、记录保留、可重新报名复用原记录 | ✅（主键前后一致，证明是改状态而非删了重建） |
| ④ 教师只能管理、查看自己发布的活动 | ✅（改 / 关 / 删 / 看名单四项都拦住） |
| ⑤ 已有有效报名的活动不能删除 | ✅（待审核 / 正式参加 / 候补三种占位状态**都能拦住**） |
| ⑥ 密码不以明文保存 | ✅（存的是 64 位 SHA-256，且能用正确密码校验通过） |

> 规则⑤值得特别说明：V1.5 只需要拦一种状态（`REGISTERED`），
> V2.0 变成了**三种占位状态都要拦**。如果不改 `countRegistered()` 的口径，
> 就会出现"活动上还有候补的人，教师却把活动删掉了"这种问题。
