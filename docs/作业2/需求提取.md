## 二、角色与权限边界（对应报告第五节）

| 角色 | 允许的主要操作 | 明确不能执行的操作 | 依据 |
| --- | --- | --- | --- |
| **学生** | 浏览活动列表与详情；查看活动的参加条件；报名；查看自己的审核结果与候补状态；取消报名；查看我的报名 | 发布／修改／删除活动；查看他人的报名名单；自行决定自己是否通过；停用账号 | S1、S2、T5、T7 |
| **活动组织教师** | 发布活动；设定人数上限；填写参加条件；修改／关闭／删除**自己发布**的活动；审核报名；查看**自己活动**的报名名单与已确定参加人数；按候补顺序处理名额 | 修改其他教师发布的活动；代替管理员停用账号；查看自己活动之外的报名名单 | T1、T2、T3、T4、T6、T7 |
| **系统管理员** | 查看平台全部活动（监督用途）；查看全部用户账号及状态；停用账号；恢复账号 | 处理具体报名；审核报名；代替教师决定参加条件 | A1、A2、A4 |
| 系统管理员（**待确认**） | 是否负责**审核教师发布的活动**——A3 未正面回答，无法判定 | —— | A3 |

**边界结论**：三个角色的职责可以概括为——
**教师定规则、学生受规则约束、管理员只保证账号与内容不出问题，不介入业务判定。**
其中最稳定的一条是管理员的边界（A1 与 A4 两条独立回答互相印证），
最模糊的一条也正是管理员与教师之间那条线（A3）。

| 编号 | 冲突 / 张力 | 涉及证据 | 分析 |

## 五、对 V1.5 的影响面（对应报告第七节）

### 5.1 数据库（三张表都要动）

| 表 | V1.5 现状（`db/schema.sql`） | V2.0 需要的改动 |
| --- | --- | --- |
| `user` | `role` 只有 `STUDENT` / `TEACHER`；**没有状态字段** | `role` 增加 `ADMIN`（REQ-V2-12）；新增 `status`（`ACTIVE` / `DISABLED`）支撑停用与恢复（REQ-V2-15、REQ-V2-16） |
| `activity` | 无人数、无条件字段；`status` 已定义 `OPEN` / `CLOSED` / `FINISHED` | 新增 `capacity`（人数上限，REQ-V2-01）与 `eligibility`（参加条件，REQ-V2-03） |
| `activity_registration` | `status` 只有 `REGISTERED` / `CANCELLED` 两态 | `status` 扩展为多态（待审核→未通过／条件通过→候补／正式参加）；新增记录**进入候补时间**的字段（REQ-V2-07） |

**一个可以复用的点**：`uk_reg_student_activity (activity_id, student_id)` 唯一约束
在候补模型下依然成立——一个学生在同一活动上**始终只有一行记录**，状态流转都改这一行。
这与 V1.5 中「取消报名改 `status` 而不删记录、重新报名复用原行」的做法完全一致，
**因此唯一约束不需要改**。这一点可以直接写进报告作为「V1.0 的数据设计经得起需求变化」的证据。

### 5.2 后端

| 类别 | 内容 |
| --- | --- |
| **新增** | `AdminApi`（全部活动总览、用户列表、停用／恢复账号）；`RegistrationService` 的审核、候补、递补、正式参加人数统计 |
| **改造** | `ActivityService`（`capacity` / `eligibility` 的录入与校验）；`RequestContext.requireRole`（支持 `ADMIN`）；`AuthApi` / `SessionManager`（被停用账号不得登录） |
| **不受影响** | `DBUtil`、`PasswordUtil`、`JsonUtil`、`ApiRouter` 的路由匹配与统一响应机制、DAO 的参数化 SQL 写法与资源关闭方式 |

### 5.3 前端

| 类别 | 内容 |
| --- | --- |
| **新增** | 管理员端 2 个页面：活动总览（监督）、用户管理（停用／恢复） |
| **改造** | 教师端：活动管理表单增加「人数上限」「参加条件」；报名名单按 **待审核 / 候补（含位次）/ 正式参加** 分组展示 |
| **改造** | 学生端：活动详情显示**参加条件**与自己的报名状态；我的报名显示审核结果与**是否仍在候补等待中**（按 S5，只需状态、无需精确位次） |
| **改造** | `router/index.js` 守卫与 `App.vue` 侧边菜单增加 `ADMIN` 分支 |
| **不受影响** | `api/request.js` 的拦截与错误码处理、`stores/auth.js` 主体逻辑、`styles/global.css` 布局 |

### 5.4 总体影响说明（可直接写入报告的段落草稿）

> 本轮需求变化集中在**报名流程的状态模型**上，而不是全新的业务领域。
> V1.5 把「报名」实现为一个两态记录（已报名／已取消），
> 而访谈结论（T6）要求「审核通过」与「正式参加」分离，T2 又要求候补按时间排队，
> 因此报名记录需要从两态扩展为一条带顺序的状态链。
> 相应地，数据库三张表都要增量修改，业务层与界面层需要较大调整。
> 但**分层结构本身没有被推翻**：数据访问层的 SQL 封装、统一响应格式、
> 令牌与角色校验机制、以及 V1.0 已确认的六项业务规则全部继续有效，
> 说明 V1.0 的分层设计对需求演化是友好的。
> 新增的「系统管理员」角色也验证了这一点——它只是新增一条界面分支与一组接口，
> 没有导致任何已有代码重写。

## 六、开放问题的最小假设决策（对应报告第八节）

> **为什么用"最小假设"，而不是替被访者猜一个答案**：
> 报告模板要求「没有发生的内容不要补写」。
> 因此对反复追问仍无法确认的问题，本轮不编造结论，
> 而是统一选择**实现代价最小、附加假设最少**的方案：
> 能不做的功能不做，能沿用 V1.5 的沿用，必须新做的只做规则最明确的那部分。
> 这样即使后续确认结果与假设不同，返工代价也最小。

| 编号 | 对应开放问题 | 最小假设（本轮按此实现） | 选择理由 | 若后续确认不同的改动代价 |
| --- | --- | --- | --- | --- |
| A1 | G5 发布审核 | **不做活动发布审核流程**，教师发布后立即可见 | T8 描述现状时完全没有提到审核环节，即现状无审核；新增审批流是最大的一块工作量 | 中：需加活动状态、管理员审核页面与接口 |
| A2 | G1 账号创建 | **沿用 V1.5 的自助注册**，不新增管理员建号功能 | V1.5 已有可用实现，改动为零 | 中：需加管理员端用户新建／导入 |
| A3 | G3 条件内容 | `eligibility` 用**自由文本（一句话说明）**，不做结构化条件、不做自动判定 | 教师三次都没说清条件内容，结构化设计没有依据 | 小～中：若确认是年级／专业，需加字段并改审核逻辑 |

| A5 | G6 截止时间 | **不设报名／取消截止时间**，沿用 V1.5 随时可取消 | 无证据支持，且不加不影响其他规则 | 小：加一个时间字段与两处校验 |
| A6 | G7 递补方式 | **教师端手动递补**：候补按进入候补的时间排序展示，教师点「递补给此人」 | T2 明确了顺序却没说自动；手动实现不需要额外状态，也不需要通知与超时机制 | 中：需改为自动触发＋通知确认＋超时处理 |
| A7 | G8 审核范围 | **所有报名统一进入待审核**，不做「无条件活动跳过审核」的特例 | 统一处理最简单、假设最少；T4 表明条件由教师定，那就统一交给教师审 | 小～中：需增加自动通过分支 |
| A8 | G10 停用后报名 | **账号停用不自动取消其报名**，原记录保留，教师在自己的名单里看到并处理 | A6 把报名相关事宜推给教师，与 REQ-V2-17 的权限边界一致 | 小～中：若改为自动取消，需联动释放名额并触发递补 |

### 6.1 最小假设下的报名状态机

A6（手动递补）与 A7（统一审核）共同决定了状态数量。
在最小假设下，报名记录只需要 **5 个状态**：

```
报名提交
   ↓
PENDING_REVIEW（待审核）
   ├── 教师判定不符合条件 ──→ REJECTED（未通过）
   └── 教师通过 ─┬─ 有名额 ──→ CONFIRMED（正式参加）
                 └─ 已满 ───→ WAITLISTED（候补，按进入候补的时间排序）
                                   │
                     教师手动递补 ──┘──→ CONFIRMED

任意状态 ──→ CANCELLED（已取消，V1.5 已有，可重新报名复用原记录）
```

**关键点**：

1. **不需要「待确认递补」这一中间状态**——因为 A6 把递补做成教师手动执行，
   不涉及通知与超时；若将来改为自动递补，就必须补上这个状态。
2. **`PENDING_REVIEW` 是新增的**，它取代了 V1.5 的 `REGISTERED`。
   在 A7 下所有报名都先进入待审核。
3. **`WAITLISTED` 必须有排序依据**，即记录「进入候补的时间」（来自 T2）。
4. 数据库唯一约束 `uk_reg_student_activity` **继续有效**：一个学生在同一活动上仍只有一行记录，
   状态流转都改这一行，与 V1.5 的做法一致。
